## 没有照抄的表述及原因

| 建议中的表述 | 本文采用的准确说法 |
|---|---|
| core 回放适合大量 watch | 普通 core 只有状态快照，没有后续执行；追查写入需活进程复现或另外的执行录制能力 |
| 生产 release 不要用 -g | -g 可与 -O2 共用；生产可保存单独调试符号，按发布策略决定是否分发 |
| systemd、容器不受 ulimit 控制 | 目标进程仍有资源限制；另一个终端的修改不自动传递给服务。管道 core 收集有特别语义 |
| mutex 先自旋，失败才 futex | 无竞争通常是用户态原子快路径；是否先自旋取决于实现与锁类型 |
| 线上优先收集 core，就无需暂停 | 已有崩溃现场可离线分析；在线 gcore 仍会暂停和增加 I/O，不能为了取证让业务崩溃 |
| 新编译同名程序必然全部错乱 | 关键是制品、库、符号是否匹配；不能凭文件名代替核对，也不能把可复现构建一概视为不匹配 |

## 第二轮小幅校订

- 补明独立 gcore 正常完成后目标继续运行，交互式 GDB 转储不自动 continue；转储暂停时长不保证很短。
- 补明 tcpdump -C 使用十进制 MB，文件可略超轮转阈值；不把阈值误当严格空间上限。
- 说明 strace 过滤集合的“类别 + 具体系统调用”含义，futex 不属于 network。
- 补充 set pagination off 与 -F 99 的含义，强调不要盲目提高采样频率。
- 强化单向抓包不能独自证明故障，保留 CLOSE_WAIT 持续堆积需进一步验证的判断。
- 区分 Little 的平均值适用条件与 Amdahl 的时间分解假设，没有照抄“一律禁止非平均值”的概括。
- 正文及小抄统一为反引号代码围栏；Bash、C、Python 代码内容与已核查版一致，不重复运行这些命令。页面重新检查。
- 未泛化“部分系统 tcpdump 自动写 pcapng”，改为按实际文件格式与分析器版本判断兼容性。
