# C++11～C++26 新特性：每个标准在补哪个坑

## 为什么返回一个大对象要付两次拷贝

先看一个真实会发生的场景：订单服务每次查询返回一个 `std::vector<Order>`，一次请求里这个 vector 被返回、被赋值、被放进缓存容器。`perf` 显示 `memcpy` 占了 40% 的时间。代码没有任何"多余"的操作——只是把对象从一个地方挪到另一个地方，但每次都真的复制了一遍堆内存。

为什么不能直接"把指针交出去"？因为在 C++11 之前，**语言里没有"这个对象我不用了"的表达方式**：只要发生拷贝，编译器只能假定源对象之后还要用，于是老老实实分配新内存、逐字节复制。

生活里的类比是交一箱书：拷贝是"复印一遍再搬走"，移动是"直接把箱子递过去"。但类比有个边界——真正被移动的不是箱子，而是**指向堆内存的指针**；而且交接后源对象并没有消失，它仍然存在、仍然会被析构，只是内容变成"有效但未指定"。

标准给出的机制是右值引用和移动构造。核心规则只有一条：**表达式的值类别决定重载决议选哪个构造函数**。

- 有名字的变量是**左值**，只能绑定到 `T&` 或 `const T&`；
- 临时对象、字面量、`std::move(x)` 的结果是**右值**，可以绑定到 `T&&`；
- 模板形参写成 `T&&` 且 `T` 需要推导时，它是**转发引用**：传左值时 `T` 推成 `U&`，靠引用折叠得到 `U&`；传右值时 `T` 推成 `U`，得到 `U&&`。

`std::move` 本身不移动任何东西，它只是一个到右值的 `static_cast`；真正搬资源的是随后被选中的移动构造函数。`std::forward<T>` 同理，只是把参数按原始值类别转回去。

三个值得注意的点：

1. **同一个对象 `b`，加不加 `std::move` 走了不同构造函数**。所以移动语义的本质是"给编译器一个信号：这个对象的资源可以抢"，而不是"把数据搬走"。
2. **`relay(c)` 拷贝、`relay(Buffer(128))` 移动**，因为 `relay` 的 `T&&` 是转发引用。如果把 `std::forward<T>` 写成 `std::move`，左值 `c` 也会被搬空——这是转发代码里最常见的错误。
3. **`vector` 扩容时走的是移动而不是拷贝**，因为移动构造标了 `noexcept`。这背后是标准库的异常安全契约：扩容要保证"要么成功、要么原封不动"，如果移动构造可能抛异常，搬到一半失败就无法回滚，于是 `std::move_if_noexcept` 选择退化成拷贝。**这就是"移动构造必须加 `noexcept`"的原因**，不是风格偏好。

边界要说清：`const` 对象上 `std::move` 得到 `const T&&`，匹配不上 `T&&`，会静默退化成拷贝；内置类型（`int`）的移动就是拷贝；移动过的对象只能析构或重新赋值，读它的内容是未指定行为。另外这份示例为了突出调用顺序，删掉了移动赋值、自赋值与异常安全处理，真实资源类还要满足"五法则"或干脆用 `=default` 让编译器生成。

版本线索：移动语义与右值引用是 C++11 的标志；C++14 补了函数返回值推导与 `decltype(auto)`；C++17 把"临时对象的拷贝消除"从"允许"变成**必须**，所以 `T x = T();` 这类写法在新标准下不再要求类型可拷贝——这也是为什么有些"老代码能过、新代码反而报错"的奇怪现象，其实是编译器的省略行为变了。

## 为什么资源总要手写 delete

第二个坑更常见：函数里 `new` 了一块内存，中途某个分支 `throw` 或者提前 `return`，`delete` 就走不到了。代码评审时看一遍看不出来，线上跑一个月泄漏一次。

根本原因是"释放"这一步没有绑定在"作用域结束"上。RAII 就是把"释放"放进析构函数：无论从哪条路径离开作用域，析构都会被调用——异常展开时也一样。智能指针是 RAII 针对"堆对象所有权"的标准化实现。

类比是酒店房卡：`unique_ptr` 是"只有一张房卡，转手时卡给下一个人，自己就刷不开了"；`shared_ptr` 是"多张卡共享同一个房间，最后一张卡退还时房间才清空"；`weak_ptr` 是"能看一眼房间有没有人，但不能把人锁在里面"。

四个必答点：

1. **`unique_ptr` 只移动不拷贝**，大小与裸指针相同（默认删除器是空类，享受空基类优化），是真正的零成本抽象。
2. **`make_shared` 只做一次分配**：控制块与对象在同一块内存里。代价是只要还有 `weak_ptr` 活着，对象那部分内存也回收不了。
3. **循环引用会泄漏**：`A->next = B` 与 `B->next = A` 让两个 `use_count` 都停在 1，离开作用域也不析构。解决方式是把其中一个方向改成 `weak_ptr`——示例里 `b->back` 是 `weak_ptr`，所以两个节点都正常析构了。用 `weak_ptr` 之前必须 `lock()`，否则对象可能已经没了。
4. **`shared_ptr` 的线程安全有明确边界**：引用计数的增减是原子的，所以多个线程可以同时拷贝/销毁同一个 `shared_ptr`；但它指向的**对象本身不是线程安全的**。面试问"`shared_ptr` 线程安全吗"，答"计数安全、对象不安全"才是完整答案。

这份示例只演示所有权与生命周期，没有涉及自定义分配器、`enable_shared_from_this`、多线程同时拷贝同一个 `shared_ptr` 的实际验证。真实工程里还要考虑：`shared_ptr` 的原子操作在热路径上并不便宜，能 `unique_ptr` 就别 `shared_ptr`。

版本线索：智能指针是 C++11 引入（`auto_ptr` 在 C++17 被彻底移除，因为它"拷贝即转移所有权"，放进容器会静默变成空指针）；C++14 补了 `std::make_unique`；C++20 的 `[[no_unique_address]]` 让无状态删除器/分配器的空对象真正不占空间。

## 为什么模板报错读不懂

写一个泛型函数，要求"T 要能比较大小"。C++11/14 只能把要求写在注释里，或者用 `static_assert` 在函数体里断言。一旦调用方传了不满足的类型，报错不是"这个类型不能比较"，而是从 `std::vector` 内部某一行开始、几百行的实例化回溯。

为什么编译器不能早报错？因为模板的约束在 C++20 之前只存在于注释和文档里，语言没有"命名一条约束"的能力。SFINAE 能让"替换失败不算错误"，但它是靠"让某个表达式非法"来实现的，报错位置依然在深层。

类比：老的招聘流程是先入职再考核，不合适的时候人已经在工位上；concepts 相当于把岗位要求写进 JD，简历不符在筛选阶段就退回，而且告诉你缺哪一条。

要点：

1. `concept` 是"一组布尔约束的命名"。本例 `IntRange` 要求"是 range，且元素类型恰好是 `int`"。
2. `requires` 有两种写法：`requires std::integral<T>` 是约束子句；`requires(T t) { t.foo(); }` 是 requires 表达式，用来检查表达式是否合法。
3. **concepts 参与重载决议**：多个重载都满足时，编译器按"约束更强"的那个优先（这叫约束包含/偏序），这比 SFINAE 时期"谁更特化"的规则更好预测。
4. `operator<=>` 加 `=default` 让编译器按成员顺序生成比较，并合成 `<`、`<=`、`>`、`>=`；但**它不生成 `==`**，需要另写。

边界：concepts 只能检查"接口层面"的合法性，不能检查函数体内部是否正确；它也不会替代文档——一个 concept 名字起得含糊，读者还是不知道具体要求什么。另外 `std::format` 的格式串在 C++20 要求是常量表达式，例子里的常量串没问题，运行期拼接得用 `std::vformat`。

顺带把这条线的历史补齐：C++11 给了 `static_assert` 与 `decltype`（能在编译期断言、能推导表达式类型）；C++17 给了 `if constexpr`（按条件丢弃分支，不再要求两个分支都能编译）；C++20 才把"约束"变成一等公民。

## 为什么同一段逻辑要给每种类型写一遍

C++11 之前，写一个"打印容器里所有元素"的函数，要么用模板 + 手写迭代器，要么为每种类型写一遍。`auto`、范围 `for`、`lambda` 分批解决了"少写样板"，但它们各自有推导规则，规则不熟就会写出编译器能过、行为不对的代码。

`auto` 的推导规则沿用模板实参推导：**顶层 `const` 与引用会被丢掉**。`decltype` 相反，它忠实反映表达式类型；其中 `decltype((x))`（带括号）是"表达式"而不是"变量名"，左值表达式会被推成引用类型。

```cpp
{{SRC:auto.cpp}}
```

保存为 `auto.cpp`，编译运行（只用到 C++11/14 的特性）：

```bash
g++ -std=c++14 auto.cpp -o auto
./auto
```

实际输出：

```text
{{OUT:auto}}
```

三个坑，全是标准规定、不是实现差异：

1. `auto a2 = ref;` 拿到的是**拷贝**，要引用必须写 `auto&`；`auto a3 = cn;` 丢掉了 `const`。
2. `decltype(n)` 是 `int`，`decltype((n))` 是 `int&`——多一层括号就从"变量"变成"表达式"。写 `decltype(auto)` 返回类型时，这个区别决定返回的是值还是引用。
3. **`std::vector<bool>` 是特化**，`operator[]` 返回代理类而不是 `bool&`。`auto b = bits[0]` 推出代理类型（本例 16 字节，而 `bool` 是 1 字节），所以 `b = true` 真的写穿了容器；`bool c = bits[1]` 才是拷贝。想拿真正的值就显式写类型。

版本线索：`auto` 与范围 `for` 是 C++11；`auto` 用于函数返回类型推导、`decltype(auto)`、泛型 lambda（`[](auto x)`）、lambda 捕获初始化是 C++14；`auto` 作形参、作模板实参、`auto` 参与 concepts 是 C++20。

## 为什么"多返回值"总是写成一堆 out 参数

一个 `parse` 函数要同时返回"成功与否""解析出的对象""错误信息"。C++11 之前的写法通常是：返回 `bool`，加一个出参引用，出错时再写一个全局错误码或抛异常。调用方必须记得检查返回值，忘记检查就静默拿到半成品。

C++17 用两个东西改了这件事：**`std::tuple` + 结构化绑定**（直接拆出多个值），以及把元组摊开成实参的 `std::apply`、展开参数包的**折叠表达式**。

类比：以前是"一个信封只能装一封信，其余信息写在便签上到处贴"；现在是"一个信封按顺序装多张纸，取的时候按位置命名"。

两个例子合起来的要点：

1. **结构化绑定能拆 `pair`、`tuple`、数组、聚合体**，写 `auto& [k, v]` 是引用绑定，改的是原对象；它本质是给成员起别名，不能跳过某个成员。
2. **CTAD** 让 `std::pair p{1, 2.5}`、`std::tuple t{1, std::string("two")}` 省掉模板实参。注意与 `initializer_list` 的歧义：`std::vector v{1, 2}` 是两个元素，要"两个元素的初值"得写 `std::vector v(1, 2)`。
3. **折叠表达式有四种形式**（`(xs + ...)`、`(... + xs)`、带初值的两种）。示例写 `(xs + ... + 0)` 用 `0` 做初值，**这样空参数包也能编译**——空包是最容易漏的边界。
4. **逗号折叠 `((f(x)), ...)`** 是"对每个参数执行一次"的惯用法，外层括号不能省，否则会变成丢弃结果的逗号表达式。
5. **`std::apply` 把 tuple 摊成实参，`std::invoke` 统一函数/成员函数指针/数据成员的调用方式**，写泛型代码（线程构造、`function`）都靠它。

边界：结构化绑定在 C++17 里**不能**被 lambda 捕获（C++20 才放开）；`CTAD` 在 `std::vector v{1,2}` 这种场景会选 `initializer_list` 构造，容易误判元素个数；`std::apply` 要求元组大小与形参个数严格匹配，编译期报错但信息依然不短。

版本线索：`tuple`、`initializer_list`、范围 `for` 是 C++11；`auto` 返回类型推导、泛型 lambda 是 C++14；结构化绑定、`if constexpr`、折叠表达式、CTAD、`apply`/`invoke` 是 C++17；模板 lambda（`[]<class T>(T)`）是 C++20。
