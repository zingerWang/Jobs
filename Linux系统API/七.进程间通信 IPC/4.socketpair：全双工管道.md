# Linux `socketpair`：原生全双工管道详解

在了解了半双工的匿名管道（`pipe`）和有名管道（`FIFO`）之后，如果需要在亲缘进程（或同一个进程）之间实现**高效的套接字级双向通信（Full-Duplex）**，调用两次 `pipe()` 建立双管道固然可行，但更地道、性能更优的选择是使用 **`socketpair`**。

在 Nginx、Redis、Chromium 等高性能开源项目中，`socketpair` 被广泛用作**主进程与子进程/工作进程之间的控制信道（Control Channel）**、**进程间文件描述符传递（FD Passing）**以及**事件唤醒机制**。

---

## 一、 核心概念与关键细节

* **原生全双工（Full-Duplex）**：
与 `pipe()` 创建的单向通道不同，`socketpair()` 一次性创建**一对相互连接的无名套接字（Socket Pair）**。向 `sv[0]` 写入的数据可以从 `sv[1]` 读出；向 `sv[1]` 写入的数据可以从 `sv[0]` 读出。
* **基于套接字 API（`AF_UNIX` / `AF_LOCAL`）**：
在内核底层使用 **UNIX 域套接字（UNIX Domain Socket）** 实现。支持 `read()` / `write()`，也支持 `send()` / `recv()` 以及传递文件描述符的 `sendmsg()` / `recvmsg()`。
* **限制：仅限亲缘进程**：
由于没有文件系统路径名，**无法被无亲缘关系的独立进程直接通过路径 `open()` 打开**。无亲缘进程若想使用 UNIX 域套接字通信，需要使用标准的 UNIX 域 Socket（即 `bind()` 到一个具体的文件路径上）。

---

## 二、 生产实践中的核心坑点与细节

### 1. `SOCK_STREAM` 粘包与消息边界

* **`SOCK_STREAM`（常用）**：提供类似 TCP 的字节流服务，**没有消息边界**。多次 `write()` 的数据可能会被内核合并，`read()` 可能会读到半条或多条消息。因此业务层必须自行设计报文协议（如：**固定长度头 + Body** 或 **特定分隔符**）。
* **`SOCK_DGRAM`**：保留消息边界（写入一次对应读取一次），但有单次报文长度限制（受内核缓冲区限制）。

### 2. 为什么必须关闭多余的文件描述符（深入内核引用计数）

调用 `fork()` 后，父子进程的 `sv[0]` 和 `sv[1]` 引用计数均为 2。

* **坑点**：如果父进程不关闭 `sv[1]`，当子进程退出或关闭其 `sv[1]` 时，`sv[1]` 在内核中的引用计数变为 1（父进程依然持有）。
* **后果**：内核**不会**向对端（`sv[0]`）触发 `EOF`，导致父进程在 `read(sv[0])` 时会**无限阻塞**而无法检测到子进程已退出。

### 3. 阻塞 / 非阻塞行为与 `SOCK_CLOEXEC`

* **默认阻塞**：缓冲区满时 `write()` 阻塞；缓冲区空时 `read()` 阻塞。
* **非阻塞设置**：可以在调用时直接追加位掩码 `SOCK_NONBLOCK`：
```c
socketpair(AF_UNIX, SOCK_STREAM | SOCK_NONBLOCK, 0, sv);

```


在非阻塞模式下，`read()` / `write()` 无法立即完成时会返回 `-1`，且 `errno` 被设置为 `EAGAIN` 或 `EWOULDBLOCK`，业务代码需妥善处理。
* **`SOCK_CLOEXEC`（强烈推荐）**：配合 `SOCK_CLOEXEC` 标记（执行 `exec` 系列函数时自动关闭该 fd），可防止 fd 意外泄露给子进程调用的外部程序。

### 4. 管道破裂与 `SIGPIPE` 信号

若一端已关闭（`close`），另一端继续调用 `write()` / `send()` 写入数据时，内核会向写入进程发送 **`SIGPIPE`** 信号。该信号的默认动作是**直接杀死进程**。

* **生产防坑**：服务程序通常需要在初始化时忽略或屏蔽该信号：
```c
signal(SIGPIPE, SIG_IGN);

```

## 三、 代码示例

### 示例 1：父子进程全双工双向通信

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <sys/types.h>
#include <sys/socket.h>
#include <sys/wait.h>
#include <signal.h>
#include <errno.h>

int main() {
    int sv[2];
    char buf[1024];

    // 生产实践：忽略 SIGPIPE，防止对端关闭导致进程崩溃
    signal(SIGPIPE, SIG_IGN);

    // 1. 创建全双工 UNIX 域套接字对，同时带上 NONBLOCK 和 CLOEXEC
    if (socketpair(AF_UNIX, SOCK_STREAM | SOCK_CLOEXEC, 0, sv) == -1) {
        perror("socketpair");
        exit(EXIT_FAILURE);
    }

    pid_t pid = fork();
    if (pid < 0) {
        perror("fork");
        exit(EXIT_FAILURE);
    }

    if (pid > 0) {
        // === 父进程 ===
        // 关键：必须关闭父进程用不到的 sv[1]，否则子进程 close 时无法触发 EOF
        close(sv[1]);

        const char *parent_msg = "Ping from Parent";
        write(sv[0], parent_msg, strlen(parent_msg) + 1);
        printf("[Parent] Sent: %s\n", parent_msg);

        ssize_t n = read(sv[0], buf, sizeof(buf));
        if (n > 0) {
            printf("[Parent] Received reply: %s\n", buf);
        }

        close(sv[0]); // 父进程关闭，触发子进程 read 返回 0 (EOF)
        wait(NULL);
    } else {
        // === 子进程 ===
        // 关键：必须关闭子进程用不到的 sv[0]
        close(sv[0]);

        ssize_t n = read(sv[1], buf, sizeof(buf));
        if (n > 0) {
            printf("  [Child] Received: %s\n", buf);
        }

        const char *child_reply = "Pong from Child";
        write(sv[1], child_reply, strlen(child_reply) + 1);
        printf("  [Child] Sent reply: %s\n", child_reply);

        close(sv[1]);
        _exit(EXIT_SUCCESS);
    }

    return 0;
}

```

### 示例 2：跨进程传递文件描述符（FD Passing）

这是 `socketpair` 独有且最强大的能力，底层基于 `sendmsg()` 与 `recvmsg()` 操作 `SCM_RIGHTS` 辅助数据（Ancillary Data）。

#### 🎯 核心作用：传递的是“能力”，而非“名字”

传统的进程间协作，通常靠**路径名**（如 `"/tmp/data.txt"`）来共享文件。但路径名只是一个“名字”，存在被篡改、文件被移动或替换的安全风险（如TOCTOU攻击）。

`SCM_RIGHTS` 传递的是**文件描述符（File Descriptor）**，它在内核中直接指向一个已打开的**文件对象（File Object）**，这个对象包含了文件状态、读写偏移量、访问模式等所有关键信息。因此，FD传递的本质是**将“访问某个内核对象的能力”从一个进程直接移交给另一个进程**，接收方无需知道该对象的名字或路径，就能直接操作它。

#### 🚀 主要优势：为何是不可替代的机制

相较于“通过路径名重新打开文件”的传统方式，FD传递在多个维度上具有压倒性优势：

**1. 安全性与可靠性：彻底规避竞态条件**
这是最根本的优势。接收方基于FD操作，完全绕开了路径名解析过程。无论文件在文件系统中如何被移动、重命名或替换，FD始终指向最初打开的那个**内核对象**，从根本上杜绝了**路径竞态条件（Race Condition）** 和 **TOCTOU（检查时间与使用时间不一致）攻击**。

**2. 效率：避免开销，共享状态**
*   **避免重复打开**：发送方已经完成了 `open()`、`socket()` 等系统调用的开销（路径查找、权限检查等），接收方直接获得一个可用的FD，无需再次打开，这在处理高频交互时性能提升显著。
*   **共享文件偏移量**：传递的FD与发送方的FD在语义上等同于 `dup()`，它们**共享同一个打开文件表项**。这意味着**两个进程会共享文件的读写偏移量**。进程A读取10字节，进程B下一次读取就会从第11字节开始，这种天然的同步机制在某些协作场景中非常有用。

**3. 通用性：可传递任何类型的内核对象**
传递的不仅是“文件”。任何能用文件描述符表示的内核对象都可以传递，包括**套接字（Socket）、管道（Pipe）、共享内存对象（memfd）、甚至另一个进程的套接字连接**等。这使得它成为一种极其通用的进程间能力传递机制。

**4. 解耦与权限转移**
与 `fork()` 后子进程被动继承父进程的所有FD不同，FD传递允许在**两个不相关的进程**（甚至跨越容器/Pod边界）之间，主动、精确地**授予**对特定资源的访问权限，而不需要传递整个进程的上下文。这为构建模块化、松耦合的系统架构提供了基础。

#### 💎 典型应用场景

正是基于以上优势，FD传递在诸多底层系统中扮演着关键角色：

*   **高性能服务器/数据库**：主进程监听端口，接受连接后，通过 `SCM_RIGHTS` 将已建立的**套接字FD**传递给空闲的工作进程（Worker Process）来处理。这实现了负载均衡，且避免了多个进程竞争 `accept()` 连接的“惊群”问题。
*   **多线程程序的竞态防护**：在多线程环境中，`fork()` 和 `pipe()` 的时序可能意外地复制管道端点，导致死锁。通过 `socketpair` 和 `SCM_RIGHTS` 精确地传递管道读端，可以构建**无竞态（race-proof）** 的子进程通信通道。
*   **热升级与零停机**：旧版本的服务进程可以在 `exec` 执行新版本二进制文件之前，将当前监听的所有**套接字FD**通过环境变量或辅助通道传递给新进程。新进程启动后即可直接使用这些FD继续服务，实现无缝热升级。
*   **微服务/容器间的数据共享**：在Kubernetes等环境中，可以通过共享卷上的Unix套接字，在隔离的Pod之间传递FD，实现对特定文件或远程连接的**直接访问**，而无需暴露文件路径或网络地址。

`SCM_RIGHTS` 的FD传递机制，是将**内核对象的能力**作为一种“一等公民”在进程间进行安全、高效、通用地移交，它是构建健壮、高性能系统软件的基石之一。

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/socket.h>
#include <sys/wait.h>

// 功能：通过UNIX域套接字发送一个文件描述符fd
// sock：socketpair通信端点fd；fd_to_send：待传递给对端的文件描述符
int send_fd(int sock, int fd_to_send) {
    struct msghdr msg = {0};       // sendmsg/recvmsg使用的消息头结构体，承载普通数据+控制辅助消息，初始清零
    char buf[1] = {0};             // 规定：使用SCM_RIGHTS传递FD时，必须附带至少1字节普通数据，哪怕无业务含义
    struct iovec iov = {.iov_base = buf, .iov_len = 1}; // iovec分散缓冲区，指向上面1字节缓冲，长度1

    // CMSG_SPACE：计算控制消息占用总大小（包含内存对齐填充，分配缓冲区必须用这个宏，不能直接sizeof(int)）
    char cmsgbuf[CMSG_SPACE(sizeof(int))];

    msg.msg_iov = &iov;            // 将普通数据缓冲区挂载到消息头
    msg.msg_iovlen = 1;            // iovec数组元素个数，这里只有1块缓冲区
    msg.msg_control = cmsgbuf;     // 指向存放辅助控制消息（cmsg）的缓冲区
    msg.msg_controllen = sizeof(cmsgbuf); // 控制缓冲区总字节大小

    // CMSG_FIRSTHDR：从msghdr取出第一条控制消息头cmsghdr的指针
    struct cmsghdr *cmsg = CMSG_FIRSTHDR(&msg);
    cmsg->cmsg_level = SOL_SOCKET; // 控制消息层级，传递文件描述符固定为SOL_SOCKET
    cmsg->cmsg_type = SCM_RIGHTS;  // 控制消息类型：SCM_RIGHTS代表传递打开的文件句柄FD
    cmsg->cmsg_len = CMSG_LEN(sizeof(int)); // CMSG_LEN：控制消息有效长度（不含对齐padding，赋值给cmsg_len）

    // CMSG_DATA：拿到cmsghdr后面负载数据的起始地址，写入待发送的fd编号
    *(int *)CMSG_DATA(cmsg) = fd_to_send;

    // 发送复合消息：1字节普通数据 + 携带FD的控制辅助消息，flag=0默认阻塞发送
    return sendmsg(sock, &msg, 0);
}

// 功能：从UNIX域套接字接收对方传递过来的文件描述符，成功返回收到的fd，失败返回-1
int recv_fd(int sock) {
    struct msghdr msg = {0};
    char buf[1];                   // 和发送端对应，接收配套的1字节普通数据
    struct iovec iov = {.iov_base = buf, .iov_len = 1};

    char cmsgbuf[CMSG_SPACE(sizeof(int))]; // 接收侧控制消息缓冲区，同样预留对齐空间
    msg.msg_iov = &iov;
    msg.msg_iovlen = 1;
    msg.msg_control = cmsgbuf;
    msg.msg_controllen = sizeof(cmsgbuf);

    // 阻塞接收消息；返回值<=0代表对端关闭或者出错，直接返回-1
    if (recvmsg(sock, &msg, 0) <= 0) return -1;

    // 获取第一条控制消息头
    struct cmsghdr *cmsg = CMSG_FIRSTHDR(&msg);
    // 校验控制消息层级和类型，确认是传递FD的消息
    if (cmsg && cmsg->cmsg_level == SOL_SOCKET && cmsg->cmsg_type == SCM_RIGHTS) {
        // 取出内核在本进程中新分配的fd编号（不一定和发送方fd数字相同，但指向同一个内核打开文件对象）
        return *(int *)CMSG_DATA(cmsg);
    }
    return -1;
}

int main() {
    int sv[2];
    // 创建一对相互连接的AF_UNIX全双工套接字，用于父子进程通信、传递FD
    socketpair(AF_UNIX, SOCK_STREAM, 0, sv);

    if (fork() == 0) {
        // ========== 子进程分支 ==========
        close(sv[0]);  // 最佳实践：关闭子进程不需要的端点sv[0]，避免fd引用计数残留导致read无法收到EOF
        int received_fd = recv_fd(sv[1]); // 阻塞等待父进程发送FD，接收拿到属于子进程侧的新fd
        
        char read_buf[64] = {0};
        read(received_fd, read_buf, sizeof(read_buf)); // 使用收到的fd读取文件内容
        printf("[Child] Read from passed FD: %s\n", read_buf);
        
        close(received_fd); // 使用完毕，关闭收到的文件描述符
        close(sv[1]);      // 关闭socketpair通信端点
        _exit(0);           // _exit直接退出子进程，不刷新stdio缓冲区
    }

    // ========== 父进程分支 ==========
    close(sv[1]);  // 父进程保留sv[0]，关闭自身不需要的sv[1]端点
    // 打开/创建test.txt：读写、不存在新建、存在则清空截断；权限0644 rw-r--r--
    int target_fd = open("test.txt", O_RDWR | O_CREAT | O_TRUNC, 0644);
    write(target_fd, "Hello from passed FD!", 21); // 向文件写入测试字符串
    lseek(target_fd, 0, SEEK_SET); // 将文件读写偏移重置到文件头部，否则子进程会从文件末尾读，读到空

    send_fd(sv[0], target_fd); // 通过socketpair把打开文件的fd发送给子进程
    close(target_fd);          // 父进程关闭自己这边的fd；子进程持有引用，文件不会被内核关闭
    close(sv[0]);              // 关闭父进程侧通信端点
    wait(NULL);                // 阻塞等待子进程退出，回收子进程，防止产生僵尸进程
    unlink("test.txt");        // 删除文件名；所有fd都关闭后内核才真正释放文件资源
    return 0;
}

```

msghdr
├─ msg_iov      ──> iov数组  → 普通业务数据（1字节占位）
├─ msg_iovlen       iov条目数
│
└─ msg_control  ──> cmsgbuf
                       ↓
              cmsgbuf: [ struct cmsghdr │ cmsg_data[fd] │ padding ]
                              ▲
                    cmsg 指针指向此处

## 四、 高级场景对比：`socketpair` vs `eventfd`

在事件驱动模型（如 epoll 唤醒）中，常需要实现线程/进程间的事件通知：

| 机制 | 唤醒方向 | 传输能力 | 资源开销 | 典型适用场景 |
| --- | --- | --- | --- | --- |
| **`socketpair`** | **双向** | 可以传递自定义数据、文件描述符 (FD) | 占用 2 个 FD，内核缓冲区开销相对较大 | Nginx Master/Worker 控制通道、进程间 FD 共享 |
| **`eventfd`** | 单向 | **仅维护一个 8 字节无符号计数器** | 仅占用 1 个 FD，极轻量，开销极小 | ThreadPool 任务唤醒、Reactor 事件通知 |

## 五、 管道 IPC 机制横向对比总结

| 特性 | 匿名管道 (`pipe`) | 有名管道 (`FIFO`) | 套接字对 (`socketpair`) |
| --- | --- | --- | --- |
| **通信方向** | 单向（半双工） | 单向（半双工）*（注） | **双向（全双工）** |
| **进程关系** | 亲缘进程 | 无亲缘进程 | 亲缘进程 |
| **文件系统节点** | 无 | 有（路径名） | 无 |
| **底层实现** | `pipefs` 内存循环队列 | `pipefs` 内存循环队列 | **UNIX 域套接字 (`AF_UNIX`)** |
| **传递 FD** | 不支持 | 不支持 | **支持（通过 `sendmsg` / `SCM_RIGHTS`）** |
| **典型应用** | Shell 命令管道 `|` | 独立后台服务通信 | **Nginx/Redis 线程/进程控制通道、FD 传递** |

> **注**：有名管道（FIFO）虽然支持无亲缘进程之间的通信，但其数据流**依然是单向（半双工）的**；如果无亲缘进程间需要实现双向通信，必须在文件系统中创建并打开两个独立的 FIFO 文件。
